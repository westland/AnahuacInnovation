Operational workflow and architectural blueprint

Operational workflow and architectural blueprint showing where Tavus-style conversational avatars, LLM agent systems, and multimodal AI tools to solve the core bottlenecks in ‘Innovation & Entrepreneurship’ projects at Anahuac Mayab University – particularly lack of coach capacity across ~450 teams.

Part 1: Workflow

1. Cohort Intake & Segmentation (Top of Funnel)

  • Scale: ~430–450 student teams entering in January (Enero).

  • Two Parallel Academic Tracks:

    • 2nd Semester (Innovación): Deliverable is a physical/digital prototype showcase (Feria de Prototipos).
    • 4th Semester (Emprendimiento): Deliverable is a formal venture model (Business Model Canvas - BMC).

2. The Core Bottleneck

  • “Insufficient number of coaches” / Ratio Mismatch: With ~450 teams, recruiting, training, and coordinating ~150 dedicated human coaches and judges is unsustainable or structurally impossible.

3. Phase 1: Evaluation & Filtering (Fase 1)

  • Submission Format: Teams submit their projects via a Video Pitch and supporting documents (Canvas/Prototype demos).
  • Evaluation Panel: Currently requires “5 jueces personas” (5 human judges per panel) to ensure “OBJETIVO JUSTO” (unbiased, balanced, and fair scoring).
  • Funnel Gate: Funnels 450 teams down to the 50 mejores (top 50 finalists).

4. Phase 2: Semi-Finals / Finals (2da Fase)

  • Mentoring and final judging for the top tiers:

    • 2nd Semester: Top prototype demos.
    • 4th Semester: Advanced BMC & investor-readiness pitches.

Part 3: Where Each AI Component Integrates

1. Interactive Video Avatar (Tavus-style + Realtime LLM)

  • Role: On-Demand Interactive Pitch Sparring Partner & Avatar Mentor

  • Where it fits: Before submission (Phase 1 preparation).

  • How it works:

    • Instead of waiting weeks for a 15-minute slot with a human coach, teams practice their pitch in front of a real-time conversational video avatar.

    • The avatar listens to the pitch live, uses STT (Speech-to-Text) + an LLM prompt engine, and interrupts/asks standard venture capitalist or design-thinking questions:

      • For 2nd Sem: “How did you validate this prototype with real users?”
      • For 4th Sem: “What is your customer acquisition cost (CAC) relative to LTV in your BMC?”

    • Gives students unlimited, low-stakes rehearsal repetitions with realistic facial expressions and voice feedback.

2. Local / Open-Weight Agent Systems (DeepInfra, vLLM, Ollama)

  • Role A: 24/7 Track-Specific Coaching Agents (Replacing the missing 150 coaches)

    • Architecture: Run specialized system prompts using open-source models (e.g., Llama 3 70B / Qwen 2.5 72B via DeepInfra API or self-hosted vLLM servers).
    • 2nd Sem Agent (“Prototype & Desirability Coach”): Grounded in Design Thinking, user testing rubrics, and prototype validation.
    • 4th Sem Agent (“BMC & Viability Coach”): Grounded in Alexander Osterwalder’s BMC framework, financial unit economics, and value proposition design.
    • Function: Socratic critique—the agent doesn’t write their business plan; it systematically asks for missing evidence, checks assumptions, and enforces deadlines.

  • Role B: The “5 Synthetic Judges” Panel (Simulating “5 Jueces - Objetivo Justo”)

    • Where it fits: During Phase 1 screening (450 → 50 teams).

    • How it works: Run 5 distinct agent personas per project submission to ensure fairness and prevent hallucination/bias:

      1. The Financial Feasibility Judge
      2. The Customer Problem/Validation Judge
      3. The Innovation & Uniqueness Judge
      4. The Pitch Delivery/Clarity Judge
      5. The Strict Rubric Auditor (checks compliance with academic guidelines)

    • Consensus & Outlier Check: A meta-judge agent aggregates the 5 scores, flags high-variance discrepancies, and generates a structured, multi-paragraph feedback report for the students.

Hardware for Local Implementation

Running these autonomous coaching agents locally for a cohort of 450 projects requires balancing model parameter size, VRAM footprint, and concurrency.

1. The VRAM & Model Reality Check (24GB vs. 48GB)

VRAM Setup Feasible Models Concurrency & Throughput Verdict for 450 Teams
24GB (1x RTX 3090/4090) 14B – 32B (e.g., Qwen 2.5 14B/32B Q4/Q8) High speed (~40–70 tok/s). Can serve 5–10 concurrent streams with 14B–32B. Viable with Qwen 2.5 32B; cannot run 70B.
48GB (2x RTX 3090/4090) 70B/72B (Q4_K_M / AWQ / GPTQ) OR 32B at high concurrency With 70B 4-bit, weights take ~38–40 GB, leaving only ~8 GB for KV cache (only 1–3 concurrent users). With 32B, it can serve 15–25 concurrent users. Recommended, but use Qwen 2.5 32B or Llama 3.3 70B strategically.

Crucial Insight on Model Selection: Do not force a 70B/72B model onto 48GB if you have hundreds of students. At 4-bit quantization, a 70B model leaves almost no VRAM for the KV cache (the memory needed to remember ongoing conversation context). If 5 students query it at once, it will crash or queue with high latency.

Best Practice: Run Qwen 2.5 32B Instruct (AWQ or GPTQ). In Socratic reasoning, Spanish fluency, and business logic, Qwen 2.5 32B rivals Llama 3 70B, but fits in ~18–20 GB of VRAM—leaving the remaining memory open for massive context windows and high student concurrency.

2. Hardware Architecture & Setup

  • Operating System: Linux (Ubuntu 22.04 or 24.04 LTS) is strongly recommended over Windows 11.

    • Why? Windows 11 and WSL2 introduce a ~10–15% memory overhead and latency penalties. High-throughput serving engines like vLLM are built natively for Linux.

  • GPU Configuration:

    • If using two GPUs (e.g., 2x RTX 3090 24GB): Ensure your motherboard supports PCIe bifurcation (at least x8/x8 lanes) on PCIe 4.0.

    • Power Supply (PSU): At least 1000W–1200W Gold/Platinum (transient spikes on two 3090/4090s will trip an 850W PSU).

  • System RAM: Your 64 GB DDR4/DDR5 is sufficient.

  • Storage: Run your models off a fast NVMe M.2 SSD (PCIe 4.0, \(\ge\) 1TB). Loading 40GB model weights into VRAM on startup takes seconds on NVMe vs. minutes on SATA/HDD.

3. Software Stack Setup (Step-by-Step)

Avoid basic Ollama for serving hundreds of students; Ollama lacks robust multi-user continuous batching. Use vLLM deployed via Docker.

Step 1: Base Drivers

Install NVIDIA drivers and the NVIDIA Container Toolkit on Ubuntu:

sudo apt update && sudo apt install -y nvidia-driver-550
# Install NVIDIA Container Toolkit for Docker GPU access
sudo apt install -y nvidia-container-toolkit
sudo systemctl restart docker

Step 2: Deploy vLLM with Tensor Parallelism

If you have two GPUs (48GB total), use tensor-parallel-size 2 so both cards pool memory and compute in parallel:

docker run --gpus all \
  -d \
  -p 8000:8000 \
  --ipc=host \
  --name ai-coach-engine \
  vllm/vllm-openai:latest \
  --model Qwen/Qwen2.5-32B-Instruct-AWQ \
  --tensor-parallel-size 2 \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.92 \
  --port 8000

This exposes a standard OpenAI-compatible API at http://localhost:8000/v1.

Step 3: Prompt & Agent Middleware

Run a lightweight FastAPI or Node.js service (or Open-WebUI if students need a web chat portal) that injects the track-specific system prompt:

  • 2nd Sem: Prompt pre-loaded with Design Thinking & prototype validation rubrics.
  • 4th Sem: Prompt pre-loaded with Osterwalder’s Business Model Canvas validation rules.

A. Physical Cabling (The Golden Rule)

  • Never connect the host machine via Wi-Fi. Wi-Fi induces packet jitter, head-of-line blocking, and dropped connections under high concurrency.
  • Cable: Connect the machine to the university/department switch via Cat6 or Cat6A Ethernet into a 1 Gbps or 2.5 Gbps port.
  • Set a Static Local IP for the machine (e.g., 192.168.1.150).

B. Reverse Proxy & Streaming Setup

Real-time LLM feedback relies on Server-Sent Events (SSE) for token streaming (typing effect). A raw direct port connection can hang under multi-client loads. Put Caddy or Nginx in front:

Example Caddyfile (handles HTTPS and streaming automatically):

coach.local {
    reverse_proxy localhost:8000 {
        # Disable buffering to allow smooth real-time token streaming
        flush_interval -1
    }
}

C. Student Access Strategy

  • On-Campus Labs: Students connect their laptops/phones to the university Wi-Fi (ensure it is the same subnet/VLAN) and navigate to https://coach.local or your frontend URL.
  • Off-Campus Access: If students work from home, do not open raw router ports. Set up Cloudflare Tunnels (cloudflared) or Tailscale. A Cloudflare Tunnel provides an encrypted, global HTTPS endpoint (https://coach.yourdomain.edu) without exposing the university server IP.
